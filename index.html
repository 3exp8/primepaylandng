Architecture

Three layers, one payout lifecycle.

Every instruction moves through the same disciplined path — validated, screened, reserved against a ledger, routed, and reconciled — regardless of which rail it lands on, and regardless of whether a human or an agent sent it.

01 · Orchestration

Payout orchestration layer

Receives each instruction, validates it, reserves funds against the ledger, selects the best rail, and tracks the payout through to confirmation — behind one uniform interface.

02 · Interface

Merchant & agent interface layer

A REST API and SDKs for automated flows, an MCP server for agent frameworks, a dashboard for manual payouts and approvals, and webhooks that keep your systems synced with every status change.

03 · Compliance

Compliance, risk & reconciliation

Recipient verification, sanctions screening, and velocity limits run before funds are ever reserved. Settlement is reconciled automatically against every rail's reports.

●Event-driven & auditable ●Ledger as source of truth ●Rail-agnostic by design ●Zero-trust networking ●Multi-region, active-passive
How it works

Five steps, in the order they actually happen.

This is the real sequence a payout moves through — nothing here is reordered for a pitch.

01

Instruction received

A typed request lands from your backend, the dashboard, or an agent calling create_payout over MCP. The same validation runs either way — an agent gets no shortcut past it.

02

Screening runs first

Recipient verification, sanctions and PEP screening, and velocity limits execute before a single cent is reserved. The payout cannot advance until they clear — that ordering is enforced by the code path, not documented in a runbook.

03

Funds reserved on the ledger

The amount posts to a double-entry ledger tied to your account. A balance is never just a number in a row — it's the sum of entries you can always trace back.

04

Rail selected and routed

Funds leave on whichever rail is fastest and cheapest for that currency and destination at that moment. If it degrades mid-flight, the payout reroutes instead of getting stuck.

05

Confirmed and reconciled

Webhooks fire on every state change, and settlement is reconciled automatically against each rail's own reports — so month end is a report you read, not a spreadsheet you build.

Trust & controls

Handled like it needs to survive an audit — because it does.

Prime Fast Pay is built with the controls a payout gateway needs, not the ones a checkout page can get away with.

◆

Segregated merchant funds

Merchant balances sit in accounts structurally separate from Prime Fast Pay's operating funds, reconciled daily.

✓

Screening before every reserve

Sanctions, PEP, and fraud checks run on every instruction before funds are ever reserved — not as an afterthought.

⇄

Zero-trust networking

Mutual TLS on every service-to-service call. No compute instance carries a public IP.

■

Encrypted, key-managed

AES-256-GCM at rest, TLS 1.3 in transit, ledger data protected with HSM-backed keys.

▲

Multi-region by default

Active-passive deployment across primary and disaster-recovery regions, tested with quarterly failover exercises.

≡

Full audit trail

Every payout's lifecycle is preserved as an immutable event, so any transaction can be reconstructed end-to-end.

⌘

Scoped agent keys

An sk_test_ key routes to the sandbox and never moves real money. Production keys can be scoped per tool, per amount ceiling.

◷

Human-in-the-loop approvals

Role-based approval thresholds hold an agent-initiated payout for sign-off above whatever limit you set.

⊘

Idempotent by contract

Every write takes an idempotency key, so a retrying agent can't double-send a payout.
